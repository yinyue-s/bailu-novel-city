**从数据库 → IDEA 后端 → 前端页面**的一整套开发逻辑。
---

## 一、先想清楚“要做什么功能”

以“我的书架页面”为例，你要实现的是：

- 功能：展示当前登录用户的书架列表，每本书要显示：
  - 书名、状态、简介、字数（来自 `novel` 表）
  - 分组、加入时间（来自 `bookshelf` 表）
- **后端接口**：例如 `GET /api/bookshelf/detailList`
- 返回格式：约定好统一结构，比如：

```json
{
  "success": true,
  "data": [
    {
      "shelfID": 1,
      "groupID": 2,
      "novelID": 10,
      "novelName": "xxx",
      "status": "连载中",
      "introduction": "xxxx",
      "wordCount": 123456,
      "addTime": "2025-12-02T10:00:00"
    }
  ]
}
```

先把“接口要长啥样”“每条记录要有哪些字段”想清楚，后面的工作都围绕这个来做。

---

## 二、数据库设计：先有表再有代码
以这两个表为例：

1. `novel` 表（存小说基础信息）  
   - `novelID`（主键）
   - `novel_name`
   - `status`
   - `introduction`
   - `word_count`
   - ...（其他字段）

2. `bookshelf` 表（存用户书架）  
   - `shelfID`（主键）
   - `userID`（关联用户）
   - `novelID`（关联 `novel`）
   - `groupID`（分组）
   - `addTime`（加入时间）

这一步要搞清楚：

- 主键、外键关系（`bookshelf.novelID` → `novel.novelID`）
- 字段类型（int、varchar、datetime 等）
- 是否允许为 null，是否要默认值

**先把表建好，再去写实体类、mapper。**  
否则后面 SQL、实体字段名总是对不上。
---

## 三、后端（IDEA）：按“自底向上”的顺序写

### 3.1 配置项目 & 数据源

在 IDEA 里：**配置文件很关键**
- 在 `application.yml` 配好数据库连接、驱动、MyBatis/JPA 扫描路径

---

### 3.2 写实体类（Entity）--java类

根据数据库表，在后端（idea）写实体类：

- `Novel` 对应 `novel` 表
- `Bookshelf` 对应 `bookshelf` 表

字段要和表结构对应：

```java
public class Bookshelf {
    private Integer shelfID;
    private Long userID;
    private Integer novelID;
    private Integer groupID;
    private Date addTime;
    // getter / setter ...
}
```

注意点：

- 列名和属性名不一样时，用注解或者 MyBatis 的 `resultMap` 处理，比如 `novel_name` → `novelName`。
- 这些实体主要用来**直接映射表结构**，一般不做跨表字段。

---

### 3.3 写“返回给前端的 DTO”（跨表的情况/多表连接）

因为“我的书架”要同时返回 bookshelf + novel 的字段，所以单纯 `Bookshelf` 不够，用一个专门的 VO：

```java
public class BookshelfItemVO {
    private Integer shelfID;
    private Integer groupID;
    private Integer novelID;

    private String novelName;
    private String introduction;
    private String status;
    private Integer wordCount;

    private Date addTime;
    // getter / setter ...
}
```

这里的字段名要提前在前端确定好（比如 `novelName`、`wordCount`），**以后前端就用这个结构来渲染页面**。

---

### 3.4 写 Mapper（SQL / Repository）

先从“最底层的数据访问”开始写：

- 使用 MyBatis 的话，在 `BookshelfMapper` 里写 SQL：

```java
@Mapper
public interface BookshelfMapper {

    @Select("""
        SELECT
            b.shelfID,
            b.groupID,
            b.novelID,
            b.addTime,
            n.novel_name   AS novelName,
            n.introduction AS introduction,
            n.status       AS status,
            n.word_count   AS wordCount
        FROM bookshelf b
        JOIN novel n ON b.novelID = n.novelID
        WHERE b.userID = #{userId}
        """)
    List<BookshelfItemVO> selectUserBookshelfWithNovel(@Param("userId") Long userId);
}
```

逻辑要点：

- 用 SQL 把两个表连起来；
- 用 `AS` 把列名转换成 VO 里的字段名（`novel_name AS novelName` 等）；
- 返回类型是 `List<BookshelfItemVO>`，**一条记录就是前端要展示的一本书**。

---

### 3.5 写 Service（业务逻辑层）

Service 负责：

- 参数检查（userID 是否为空）
- 封装调用 mapper
- 做一些业务判断（是否已在书架中，是否有权限等）

例如：

```java
@Service
public class BookshelfService {

    @Autowired
    private BookshelfMapper bookshelfMapper;

    public List<BookshelfItemVO> getUserBookshelfWithNovel(Long userId) {
        // 可以做一些空判断、日志等
        return bookshelfMapper.selectUserBookshelfWithNovel(userId);
    }
}
```

这里已经把“查书架+带小说信息”的功能封装成一个**后端内部方法**，上层 Controller 只需要调用它，不关心 SQL 细节。

---

### 3.6 写 Controller（对外 HTTP 接口）

Controller 把 HTTP 请求转成 Service 调用：

```java
@RestController
@RequestMapping("/api/bookshelf")
public class BookshelfController {

    @Autowired
    private BookshelfService bookshelfService;
    @Autowired
    private JwtTokenProvider jwtTokenProvider;

    @GetMapping("/detailList")
    public ResponseEntity<?> getMyBookshelfDetail(
            @RequestHeader("Authorization") String authHeader) {

        Long userID = getUserIdFromToken(authHeader);
        if (userID == null) {
            return ResponseEntity.status(401).body(Map.of(
                    "success", false,
                    "message", "未登录"
            ));
        }

        try {
            List<BookshelfItemVO> list = bookshelfService.getUserBookshelfWithNovel(userID);
            return ResponseEntity.ok(Map.of(
                    "success", true,
                    "data", list
            ));
        } catch (Exception e) {
            return ResponseEntity.status(500).body(Map.of(
                    "success", false,
                    "message", "获取书架数据失败"
            ));
        }
    }

    private Long getUserIdFromToken(String authHeader) {
        // 解析 JWT → userID
    }
}
```

这一步要保证：

- URL 路径和前端约定一致：`/api/bookshelf/detailList`
- 请求方式：`GET`
- 如何带 token：`Authorization: Bearer xxx`
- 返回 JSON 结构中有 `success`、`data` 字段

## 四、前端：按“接口 → 状态 → 渲染”的顺序来

### 4.1 定义 API 地址常量

在前端项目中，统一管理接口地址（方便以后改）：

```js
const API = {
  SHELF_DETAIL_LIST: '/api/bookshelf/detailList'
};
```

确认和后端 Controller 路径完全一致。  
***前端内容不显示，很多时候就是这一步路径或名字对不上。***

---

### 4.2 在组件里调用接口，存到状态里

以书架页面为例：

```js
const books = ref([]);
const loading = ref(false);
const errorMsg = ref('');

const loadBookshelf = async () => {
  loading.value = true;
  errorMsg.value = '';

  try {
    const res = await fetch(API.SHELF_DETAIL_LIST, {
      headers: {
        Authorization: localStorage.getItem('token') || ''
      }
    });

    if (!res.ok) throw new Error('网络错误: ' + res.status);

    const body = await res.json();
    if (!body.success) throw new Error(body.message || '获取书架失败');

    books.value = body.data || [];
  } catch (e) {
    errorMsg.value = e.message || '加载失败';
  } finally {
    loading.value = false;
  }
};

onMounted(() => {
  loadBookshelf();
});
```

注意：

- `books.value` 的每一项就是后端 `BookshelfItemVO` 的一条记录；
- 前端字段名必须和 VO 保持一致：`novelName`、`status` 等。

---

### 4.3 用模板渲染列表（`v-for`）

```vue
<div v-if="loading">加载中...</div>
<div v-else-if="errorMsg">{{ errorMsg }}</div>
<div v-else-if="!books.length">书架空空如也</div>
<div v-else class="books-list">
  <div
    class="book-item"
    v-for="book in books"
    :key="book.shelfID"
  >
    <h3>{{ book.novelName }}</h3>
    <span>{{ book.status }}</span>
    <p>{{ book.introduction }}</p>
    <span>字数：{{ book.wordCount }}</span>
    <span>加入时间：{{ formatTime(book.addTime) }}</span>
  </div>
</div>
```

这里的每一个 `book.xxx`，都对应后端 VO 的字段。  
如果后端字段名不一致，要么改 SQL 的 `AS`，要么改这里的 `xxx`。

---

### 4.4 交互类功能再逐个加（删、移分组等）

比如“从书架删除”：

- 后端：`DELETE /api/bookshelf/{shelfID}`
- 前端：
  - 调用 `fetch(API.SHELF_REMOVE + '/' + shelfID, { method: 'DELETE', ... })`
  - 若成功，从 `books`/`allBooks` 里把对应项删掉
- 一条一条把“移分组”“新建分组”等功能按照同样节奏打通。

---

## 五、整体开发逻辑总结（记这个顺序）

可以记成 7 步：

1. **先定需求和接口**  
   - 功能要做什么？  
   - URL、请求方式、返回 JSON 长啥样？

2. **设计 / 创建数据库表**  
   - 表结构、字段类型、关联关系（如 `bookshelf` ↔ `novel`）。

3. **后端实体 & VO/DTO**  
   - Entity 映射单表结构（`Bookshelf`、`Novel`）。  
   - VO/DTO 映射“对前端有意义的一条数据”（如 `BookshelfItemVO`）。

4. **Mapper/Repository：写 SQL / 查询方法**  
   - 最底层拿数据的地方，负责 join、筛选。

5. **Service：业务逻辑层**  
   - 参数校验，组合调用 mapper，处理业务规则。

6. **Controller：HTTP 接口层**  
   - 解析请求（URL、参数、Header）、获取 userID、调用 Service，并包装成统一 JSON 返回。

7. **前端：按接口写页面**  
   - 在 API 模块配置路径 → 在组件中调用接口 → 把数据存到状态 → 用 `v-for` 渲染 → 做交互（删、改、查）。
